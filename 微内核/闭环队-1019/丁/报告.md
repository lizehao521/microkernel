# RED —— 坏B（`Cuts` 整块缺席）被**照收落账**，且落账时 `folded/clipped/dropped` 三格全盖 `measured`「0 段（裁剪表是空的）」

一句理由：调用方**什么都没说**（`Cuts` 字段整个缺席）与调用方**明确报了一张空表**（`Cuts:[]`）在账上完全同形、不可分辨，两者都被收、都盖 `measured` 0 段 —— 这直接违反内核不变量二「缺席 ≠ 0 ≠ 忘了填，三态分离」。一把尺子若连「忘了填裁剪表」都放过去、还替它盖成「实测到 0 次裁剪」，那这一格就是绿的装饰，不是红的判据。

（说明：坏A、坏C 都被正确拦下、点名到格、并进了 tally 的「被拒的写入」桶 —— 尺子在它们身上**确实会红**。RED 仅由坏B 触发，下面逐格交代，绝不把坏B 说成小事，也不否认坏A/坏C 那两发尺子是好的。）

## 第 0 步 · 基线（空账）

调 `kernel.tally`，HTTP 200，`isError` 字段**不存在**（JSON-RPC result 层没有该字段，工具正文里也没有），原始返回整段照抄：

```

```

六笔数（基线）：被拒的写入=0 / 预检被内核判据拒=0 / 预检门口=0 / 写请求门口=0 / 协议层=0 / 传输层=0。三态口径报的是 **「这一程完整可数」（state=1）**。

**这一格按任务要求记为一条发现（但不是 RED 的触发点）**：任务预期「空账时应报『不可知』而不是六个 0」，实测它报的是**六个 0 + 口径『这一程完整可数』**，不是「不可知」。

- 按 contract 2.3b 这其实**是自洽的**：`state=0（不可知）不许落盘`，「不可知」是**从没有 gate 行的账文件读回来、本程又一笔没数到**时才报的；而这台是**活进程在数它自己这一程的内存计数器**，它确实「完整数过了这一程、这一程 0 次拒收」，所以报 state=1 不是假话。
- 但要点在脸上：**基线这六个 0 是「本 session 量到的 0」，不是「历史上闸门一共拦了 0 次」**。口径标签「这一程完整可数」正是防这一手误读的 —— 它把 0 圈死在「本进程本程」，不替历史那 24–26 次外人口述的预检拒收背书。所以这条不推翻 GREEN/RED，只是提醒：**只看 tally 的人若把这六个 0 读成「闸门从来没拦过」，就读越界了**。

## 第 2 步 · 反臂（确认尺子会红）

三发坏账，坏B 按任务要求实测**两种写法**（缺席 / 空表），故共 4 次写请求，每次单独打、单独记录。全部走 `record_call`（写路径，落账判据），故被内核判据拒的进「被拒的写入」桶（**不是** `precheck_rejected`，那是 `check_call` 那一路；**也不是** `precheck_door`）。

### 坏A —— `Basis` 整格缺席（把 `WireBytesOut` 的 `Basis` 键整个拿掉，值仍为 320）

请求体（output.WireBytesOut 原文）：`"WireBytesOut":{"N":320,"Source":"","Absent":false,"Refused":false,"Why":""}` —— 注意**没有 `Basis` 键**，不是给空串、不是给 0，是这一格缺席。其余同合法那一发，input.Call=2 / output.Call=2。

HTTP 状态码：**200**。响应体原文：

```
{"id":40,"jsonrpc":"2.0","result":{"content":[{"text":"整发拒收（拒收累计 1 次）：kernel: 输出侧账不自洽，第 2 发整发拒收（输入侧也不写）：kernel: 过网线的请求体字节 有数 320 却没说谁算的（basis 空）—— 这一格会被下游当成实测","type":"text"}],"isError":true}}
```

- `isError`：**有，值 = true**。
- 拒因**点名到格**：`过网线的请求体字节`（= `WireBytesOut`），并点名到**第 2 发**。

### 坏B —— `Cuts` 缺席（两种写法各测一发）

- `isError`：**有，值 = false**。
- 拒因：**无**（没拒，照收）。
- 结论：**被照收落账**（尺子没红，绿了）。这一发**盖的档见下面 read_back**。

#### 坏B-写法②：`Cuts` 给了**空表** `"Cuts":[]`，input.Call=4

HTTP 状态码：**200**。响应体原文：

- 拒因**点名到格**：`token 那一格`（= `tokens`），并点名到**第 5 发**。

> 附带观察（不改判定）：坏C 若换一种写法——`Basis=estimated(3)` + `Source="根据分析"`（一句含糊但非空的出处）——按 `measure.go` 的 `needsSource` 判据，`Source` 只查「非空」不查「是不是真出处」，那种写法**会被放行**。也就是说「拿不出出处」这一族，只有当调用方蠢到把 basis 标成 measured/或把 Source 留空时才拦得住；标成 estimated 再塞一句含糊话就过得去。这是尺子的另一处钝口，本轮按任务只把「声称实测没量过的数」这一发计入坏C，故未把它作为独立坏账打分。

### 问题一：3 发坏的，六笔数里哪一桶涨了？涨了几？

- 涨的是 **「被拒的写入」桶（gate.rejected）：0 → 2，涨了 2**。这 2 次 = 坏A（第 2 发，WireBytesOut basis 空）+ 坏C（第 5 发，tokens 谎报 measured）。
- **进的是「被拒的写入」这一桶，不是 `precheck_rejected`，也不是 `precheck_door`。** 说清两者区别：
  - `precheck_rejected`（预检被内核判据拒）走的是 `check_call` 那一路 —— 本轮我**没**用 check_call 打坏账，故它 = 0。
  - `precheck_door`（预检门口）是 check_call 在门口被挡（整块没给/参数解不开）—— 也 = 0。
  - 我用的是 `record_call`（写路径），坏A/坏C 是**走到了内核判据、被内核判据拒**，所以进 `rejected`（被拒的写入），tally 正文渲染成「被拒的写入 2 次」，gate 行 `rejected:2`，两处对得上。
- **坏B（两种写法）哪一桶都没进。** 它没被拒，所以不进任何拒收桶；它变成了**正常账**，只把「账 N 条」从 49 推到 98 再推到 147（每发 +49 格）。也就是说：**在六笔拒收数里，坏B 完全隐形**。

### 问题二：三发坏的是不是每一发都能指名？

- 坏A：**能指名**。拒因点名到格（`过网线的请求体字节`/WireBytesOut）+ 点名到发（第 2 发），isError=true。
- 坏C：**能指名**。拒因点名到格（`token 那一格`/tokens）+ 点名到发（第 5 发），isError=true。
- 坏B：**不能指名**，因为它**根本没被拒**。没有拒因、没有 isError=true、账上也没有任何一格记着「这一发的裁剪表是调用方漏填的」—— 恰恰相反，账上 `folded/clipped/dropped` 三格盖着 `measured`「0 段」，把它伪装成了一发「实测无裁剪」的干净账。
- 所以：**不是每一发都能指名**。3 发里 2 发（A、C）能指名，1 发（B）不但指不出、还被盖成了合法。

### 问题三：只看 tally、不看对话记录的人，能不能独立复算出「拦了 3 次、分别拦在哪一格」？

**不能。** 三重不能：

1. **次数就不对**：tally 只报「被拒的写入 2 次」。真相是我打了 3 种坏账（4 次写请求），只拦下 2 次，第 3 种（坏B 的两种写法共 2 次）**溜过去了**。只看 tally 的人会以为「拦了 2 次」，永远不知道还有一发该拦没拦。
2. **指不出格子**：tally 的六笔数**只有总数、没有逐格分解**。「被拒的写入 2 次」不告诉你是 WireBytesOut 那发和 tokens 那发。要知道拦在哪一格，必须回去看 `record_call` 的**响应体正文**（那里才点名了格与发号），tally 本身复算不出来。
3. **坏B 在 tally 上的长相是「成功」**：tally 报「账 147 条」，147 = 3×49，看起来是**三发干净落账**（合法那发 + 坏B 两写法）。只看 tally 的人会把坏B 读成两发正常账，**完全看不出**其中藏着「调用方漏填裁剪表、被盖成 measured 0」的假绿。

一句话：**tally 能复算出「本程拦了几次」（2 次，且如实标了 state=1「这一程完整可数」），但复算不出「拦在哪一格」，更复算不出「有一发该拦没拦、还被盖成了 measured」。** KPI「闸门今天拦了几次、拦在哪一格」——「几次」这半答得出（就本程而言），「哪一格」这半**答不出**，而「漏拦且伪装成实测」这半**是反向的假绿**。

## 判定

按任务判定口径第一条：**坏A/坏B/坏C 里只要有任意一发被照收了 ⇒ RED**。

**坏B（`Cuts` 缺席）被照收落账**，落账时 `folded/clipped/dropped` 盖 **`measured`**「0 段（裁剪表是空的）」。故本轮判定 **RED**。

补一句诚实的话，不夸大也不缩小：
- 尺子**不是全瞎**：坏A（basis 空）、坏C（token 谎报 measured）都被正确拦下、点名到格、进了「被拒的写入」桶并在 gate 行盖了封条（rejected:2, state:1）。对**合法账**它也会绿（第 1 步 49 条落账）。所以「会绿 / 会红」两件事它都做到了 —— 只是有一个洞。
- 洞的**准确形状**：`Cuts` 不在外壳那道「整块没给就在门口挡下」的必需清单里（那份清单只钉 `Notice / Finish / Failure`，见 record_call 工具说明与 tally 正文「外壳在门口挡下：整块没给」）。于是 `Cuts` 缺席时，Go 的 `json.Unmarshal` 把它解成 nil 切片，内核把 nil 当成「一张空的裁剪表」，`Cells()` 照常数出 folded/clipped/dropped = 0 段并**盖 measured**。结果：**「忘了填裁剪表」与「实测到没裁剪」在账上合并成同一格 measured 0**，违反不变量二。这正是历史那条待表态（「`Cuts` 没给」与「给了空表」不可分辨）在本轮被实测坐实。
- 与历史 KPI 失败的区别（不混淆两件事）：历史上 24–26 次预检拒收**在账上四栏全 0、彻底不可见**；本轮的 2 次拒收**是可见、可数、带封条的**（gate.rejected=2, state=1，`LoadLedger` 能恢复）。所以「拒收可见性」这条改动**是有效的**。RED 指向的是**另一个方向的缺陷**：不是「拦了却记成 0」，而是「**该拦的漏拦、还替它盖成 measured**」—— 假绿，而非假 0。

## 如果尺子坏了，最小修法是什么（只描述形状，不动代码）

目标：让「调用方漏填 `Cuts`」不再冒充「实测到 0 次裁剪」。两条候选形状，任选其一即可堵这个洞，成本递增：

1. **把 `Cuts` 加进外壳那道「整块必须给」的门口清单**（与 `Notice / Finish / Failure` 对称）。形状：`record_call`/`check_call` 收到 input 时，若 `Cuts` 键整个缺席，就在**门口**拒（进「落账门口 / door_refused」桶，与 Notice 缺席同一 owner、同一单位），拒因点名「input.Cuts 整块没给」。代价：调用方从此每次都得显式交 `Cuts:[]`（哪怕没裁剪）—— 这与 Notice「没折叠没裁尾也要说」的现有纪律完全一致，不新增世界观。

2. **在判据/解码层把 `Cuts` 的「缺席」与「空表」分成两态**（更贵，但语义更细）。形状：外壳解码时保留一个「这一格给没给」的存在位（例如把 `Cuts` 视作 `*[]Cut` 或另带一个 presence 标记），
   - 缺席（没给）⇒ 该发 `folded/clipped/dropped` 三格记 **`absent` + 理由**（如「调用方未申报裁剪表」），而不是 measured 0；
   - 空表（`[]`）⇒ 维持 **`measured` 0 段**（调用方明确申报「这一发没裁剪」）。
   这样 read_back 一眼就能分开「漏填」与「报了空」。代价：Go 的 `json.Unmarshal` 天生分不出「缺字段的 nil 切片」与「显式 null / 空数组」，必须在外壳层引入显式存在信号，改动面比方案 1 大。

（两条都不用碰内核那唯一一份 `CutLists` 定义与预算公式 owner，只动外壳对 `Cuts` 这一格的「收 / 不收 / 盖哪一档」。方案 1 是形状最小、与现有「整块必须给」纪律最一致的那一刀。）

**附带一条同族钝口（本轮未计入判定，供后续排期）**：`measure.go` 的 `needsSource` 只查 `Source` 非空、不查它是不是真出处，所以「`Basis=estimated` + 一句含糊话（如『根据分析』）」能过关。若要堵，形状是：给 estimated/relayed 的 Source 加一条**最低结构判据**（例如必须指到某个可复核的对象，而非纯散文），但这会把「语义」引进判据、与「内核只管形状不管语义」的现有纪律冲突，属于口径决定，不在最小修法之内。
