Chapter 03 · Demand Drivers

03需求驱动

本章回答：是什么在推动买方寻找“可复核的交代”？这些驱动是长期趋势，还是只在事故/审计发生时才会触发？

需求是真的，但它是触发型需求，不是“每天都要用”的需求。 合规、事故、外包交付、客户追责，这四件事发生时，买方会在很短时间内找一个“能拿出记录”的东西； 事情过去后，预算又会回到可观测性和功能开发。 这决定了销售动作：不要在平时教育市场，要在触发点上出现。

3.1 合规驱动：三条法规，三种单位

2026 年最重要的三条外部驱动是 EU AI Act 第 12 条、中国 GB/T 47746—2026、以及 OWASP MCP08。 它们都指向“可追溯”，但单位不同：EU 要的是高风险系统的事件日志，中国标准要的是应用/服务记录， OWASP 要的是MCP 调用遥测。这颗内核最贴近的是第三种，其次是第一种；第二种的单位常常是“对客承诺”， 与“模型调用”不是一回事，不能直接宣称合规。

合规驱动的三个“不要”

不要说“用了它就符合 EU AI Act”。它只提供技术记录，不提供法律结论。
不要把“高风险系统”的义务外推到所有 Agent。大多数Agent不是高风险；过度宣称会被合规买家一眼识破。
不要把“模型调用记录”当成“对客承诺记录”。后者是另一个产品（B 路线），单位不对。

合规驱动还有一个时间差：法规生效不等于预算到位。EU AI Act 的高风险义务从 2026-08-02 起适用， 但企业的合规预算通常提前 6–12 个月立项，且在第一次审计/问卷/客户追责时才会真正花钱。 所以 2026 年下半年到 2027 年上半年，是“问询增多、预算释放”的窗口；窗口里卖的是“技术附件”，不是“认证”。

3.2 技术驱动：MCP 采用了，遥测没跟上

MCP 生态的采用数据说明两件事：预算存在，且缺口存在。 公网 MCP 服务器已经超过 10,000 个；Stacklok 的调查里 41% 的组织在生产中使用 MCP； LangChain 的调查里 57% 的受访者在生产中使用 Agent，约 89% 有某种可观测性，29.5% 没有评测。 这些样本偏向活跃开发者，不能当全球普查，但足以说明“追踪/评测”已经是常规预算项。

外部读数数字对内核的含义
公网 MCP 服务器数量10,000+供给端已经形成；调用审计有对象，不需要教育“什么是 MCP”
Stacklok：组织在生产中使用 MCP41%生产采用意味着“出事故要调查”的概率上升
LangChain：受访者在生产中使用 Agent57%Agent 从 demo 走进生产，审计需求随之出现

LangChain：没有评测29.5%质量预算有缺口，但这不是内核的能力域；不要误卖

这组数据最容易被误读成“市场很大，赶紧做”。正确的读法是： 可观测性是红海，证据/拒收是红海里的一个窄缝。 89% 有可观测性，说明买方已经习惯了“看追踪”；他们不会为“再一个追踪面板”付钱， 但可能会为“追踪之后的一层签收”付钱——前提是你能证明这层签收能拦住东西、能指名格位。

3.3 事故驱动：调查需要账，但账不是防线

2026-02-27 披露的 MCPwnfluence 是一个典型：CVE-2026-27825（CVSS 9.1，任意文件写到 RCE） 加 CVE-2026-27826（CVSS 8.2，未认证 SSRF），影响 0.17.0 之前版本，有公开 PoC； 按披露方口径，受影响包的下载量逾 400 万。FreeBuf 与 Bishop Fox 的复盘都指向同一件事： 认证与边界在每一环缺席。

这类事故会带来两个需求：事前阻断和事后调查。 这颗内核只做后者的一小部分：它能告诉你“这一发调用记了什么、谁算的、哪一格被拒”， 但它不能告诉你“攻击者怎么进来的”，也不能阻止下一次。把两者混为一谈，是进入安全预算时最常见的死法。

审计层不是防线（对外材料第一屏）

如果买方问“能不能挡提示注入”，正确答案是“不能”。如果买方需要阻断，应该找 MCP 网关、WAF、DLP、访问控制。内核的价值是事后能拿出发生过什么，而不是事前不让它发生。

内部事故的说服力更强，因为它有账可查：一次 session 里，内核当面拒了 4 次不实装配 （空响应记正常收尾、类别谎报去留状态码、对端自报数标成自己量的、宣称通知发了而段里没有）。 每一次都能从账上读出“被拒的写入 N 次”并指名格位。 这不是“模型变聪明了”，而是“说错话被当场收费了”。

采购驱动最关键的不是“预算大小”，而是“谁在什么时候会主动找”。可观测性预算是常态预算，但买方不会主动找“签收层”； 合规预算是触发预算，一旦审计/问卷/追责发生，买方会在几周内找人。 所以冷启动的正确顺序是：先用开源进入可观测性预算，再用一次真实触发把签收层推进合规预算。 反过来（先打合规、再补工程）会卡在采购周期和法律审查上。

3.5 反驱动：五件会让需求消失的事

  • 大厂捆绑：LangSmith、Langfuse、Datadog 把“证据/签收”做成默认功能，价格包含在现有套餐里。
  • 开源替代：Langfuse 以 MIT 协议自托管；买方会说“我为什么不用免费的”。
  • 自建：一个工程师 2–4 周能写一个“记录 + 哈希”的版本；难点不在代码，在判据和证据，但买方常常低估后者。
  • “我们已经有日志”：买方把“调用发生过”当成“出处可核”，不认为需要额外一层。
  • Agent 项目取消：Gartner 预测到 2027 年底超过 40% 的 Agentic AI 项目会被取消；预算消失时，审计是第一个被砍的“非功能项”。

这五条反驱动里，前三条是竞争，后两条是需求本身的风险。 它们共同说明：不能做“泛审计”，只能做“触发点上的收口”。 泛审计会被免费/捆绑打掉；触发点上的收口有明确的“现在就要”的买方。

3.6 需求结论

需求是触发型的，不是常态型的

平时买方不会主动找“可复核的交代”；事故、审计、外包交付、客户追责发生时，他会在一周内找。产品的市场动作应该围绕触发点设计：让他在触发时能搜到你、能在 30 分钟试到你、能在一次 POC 里看到你拦住东西。

这也解释了为什么“研究出版 + 开源”是正确顺序：研究出版让触发时的搜索能找到你（合规/审计关键词）， 开源让触发时的工程验证能立刻开始（不需要销售、不需要合同）。两者都不需要现金投入，却正好覆盖触发型买方的两个动作。

Chapter 04 · Competitive Landscape

04竞争格局

本章回答：谁在抢同一个预算？他们的价格锚是多少？这颗内核的空白在哪里、能守多久？

竞争不是一个“同类产品列表”，而是五种不同形状的玩家从五个方向挤压同一个预算： 可观测性平台向下做证据，MCP 网关向后做审计，云厂商从基础设施向上做账本，GRC 从合规向下要运行时数据，开源/自建从价格底部往上顶。 这颗内核的空白是“窄而深的证据/拒收层”，但空白不大，且 12–24 个月内可能被捆绑。

4.2 价格锚：为什么不能按 seat 卖

可观测性市场的公开价格锚很低：29–249 美元/月的入门套餐随处可见，按 seat、按 span、按 request 计价。 如果内核按 seat 或按 span 卖，它会被直接放进同一个比价表，然后被“免费版/自带追踪”打掉。 它必须按“一次收口/一份证据包/一年私有化”计价，才能避开这个锚。

4.3 竞争定位：空白在右下角，但不大

4.4 五力：横向 SaaS 不具吸引力

“五力都强”通常意味着这个市场不该进。但对这颗内核来说，正确的结论不是“不进”，而是“不要以横向 SaaS 的方式进”。 作为窄合规组件，它可以用高单价、低销量、私有化交付绕开五力中最伤人的两条：买方比价和免费替代。 买方仍然强，但他买的不是“日志”，而是“出了事能拿出的交代”；这个价值不在 Langfuse 的比价表里。

4.5 竞争会从哪里打死它

第一条路径：可观测性平台向下做证据。LangSmith、Langfuse、Datadog 已经有追踪、评测、提示管理； 再加一个“evidence / attestation”模块，把“逐格出处 + 拒收”做成套餐功能，是完全合理的产品延伸。 它们的优势是分发和现有预算，时间窗 12–24 个月。

第二条路径：MCP 网关把审计做成默认。Microsoft、Docker、Zuplo、TrueFoundry 等控制面厂商， 已经在做认证、路由、策略；再加“调用后审计”是同一采购人的相邻需求。 它们的优势是“准入”这个必经之路，时间窗 6–18 个月。

还有两条慢路径：云厂商把“AI 审计账本”做成基础设施（AWS/Azure 的信任与合规优势）， 以及开源社区复制 49 格契约（代码可复制，证据 corpus 不可复制）。 这四条路径里，前两条最危险，因为它们不需要“相信一个新品类”，只需要在现有产品里加一个功能。

防御不是“代码更难抄”

49 格、哈希链、MCP 集成都不是壁垒。真正的壁垒是：判据表的可证伪性、拒收语义的细节、真实故障的证据 corpus、以及“外部调用方已经过了干净臂”这件事。前三个可以写出来，第四个只能跑出来。

4.6 合作而非替代：做签收层，不做追踪层

最现实的进入方式不是“替代 Langfuse/Datadog”，而是“接在它们后面”： 追踪层记录“发生了什么”，签收层记录“这句话是谁算的、能不能收”。两者用 trace ID 关联， 买方不需要换掉现有可观测性，只需要在收口处多一步“签收”。

  • 与 OTel 合作：消费 GenAI 语义约定的 span，或在 span 结束后生成一份“收口凭证”；不重复造追踪。
  • 与 Langfuse/Datadog 合作：把内核账本的指纹写回追踪，作为“可验附件”；它们有分发，内核有拒收语义。
  • 与 MCP 网关合作：网关管准入，内核管报账；“过了网关”不等于“这句话有出处”，两者互补。
  • 与 GRC 合作：GRC 管制度和风险登记，内核提供运行时证据；GRC 是证据的消费者，不是竞品。

4.7 壁垒：什么能守，什么不能守

结论：能守的是“判据 + 证据”，不是“代码 + 协议”。 这也决定了市场动作：公开判据（研究出版）、开放代码（开源）、保留证据与合规包（私有化付费）。 如果反过来——闭源判据、开源代码——既得不到标准话语，也守不住代码。

Chapter 05 · Customers & Buying Journey

05客户细分与购买旅程

本章回答：谁最可能买？谁不会买？从触发到续费，每一步需要什么证据？

最可能买的不是“想让 Agent 更聪明”的团队，而是已经在生产里跑多代理、又背了合规或外包交付责任的团队。 他们的痛点不是“模型不够好”，而是“出了事拿不出发生过什么”。 这类客户数量不多，但单价高、触发明确、愿意做设计伙伴；正好匹配这颗内核“窄而深”的形状。

主线是“平台团队做入口，受监管客户做单价，框架厂商做规模”。 平台团队最容易通过开源接上，但他们预算有限、决策快；受监管客户单价高，但采购慢、需要法律和安全审查； 框架厂商可以带来规模，但会要求 OEM 授权和深度集成。三者的顺序不能颠倒： 没有平台团队的证据，受监管客户不会信；没有受监管客户的单价，框架厂商不会认真谈。

5.2 五类反对意见，五种回答

买方说背后的真实问题正确回答
“我们能自己写”代码看起来不难；他不确定判据和证据值多少钱“代码两周能写；49 格判据、拒收语义、4 次真实拒收的证据 corpus 不是两周。你可以先拿开源版试，30 分钟接上，再决定要不要自建。”
“这能作为合规证据吗？”他要的是一个可以交给审计/监管的东西“它是技术附件，不是合规结论。它能提供逐次记录、出处、链校验；是否满足某条款，要你的法律/合规团队判断。我们不做认证。”
“能挡提示注入吗？”他把审计当成防线“不能。审计层不是防线。你需要阻断，应该用网关/WAF/访问控制；内核负责事后能拿出发生过什么。”
“为什么不用 Langfuse？”他在比价；Langfuse 免费/便宜“Langfuse 记录发生了什么；内核判断这句话能不能收，并指名哪一格拦的。单位不同。你可以两个都用，用 trace ID 关联。”
“谁来支持？一个人靠谱吗？”他在评估交付风险“私有化部署 + 支持合同 + 源码可审计；单作者是风险，我们把它写进合同和路线图，不藏着。”

这五类反对意见里，前三类必须在第一次通话就回答，不能等到 POC。 因为前三类决定“预算对不对”，后两类决定“能不能成交”。 如果第一次通话不主动说“不是防线、不是合规认证、不是能力增强”，买方会在尽调时自己发现，然后把你归类为“过度宣称”。

POC 是整条旅程的生死点。买方在 POC 里最想看到的不是“系统跑起来了”，而是“它拦住了一个我故意做坏的调用，并告诉我哪一格错了”。 所以 POC 设计必须包含一个坏发：调用方故意把 relayed 标成 measured，或把 absent 写成 0，内核必须整发拒收并指名格位。 如果 POC 只跑好发，买方会认为它只是一个“更复杂的日志”。

POC 成功判据（与唯一验收一致）

1. 账上“被拒的写入 ≥1”，且能指名哪一格、内核原话是什么；
2. 全程链自洽、sk- 0 次、没有“没量到却写成 0”；
3. 接入 ≤30 分钟，调用方模型代码零改动。

注意：这条验收今天严格 FAIL（真人外部未跑、拒收归因 5/8、缺席表达 G1）。POC 之前必须先补这三项，否则会把买方变成测试员。

5.4 非客户：五类不要追

  • 个人开发者：没有预算，也不需要审计；给他们开源版即可，不投入销售。
  • 模型实验室：自建能力强，且他们的“账”是训练数据/评测，不是调用记录。
  • 纯单轮聊天产品：没有多代理/工具调用，49 格的大部分格用不上。
  • 把审计当防火墙的团队：他们会用“能不能挡注入”验收，必然失望；不要试图教育，直接转介网关。
  • 只想让模型更准的团队：8/8 vs 6/8 是负证据；卖给他们等于自证无用。

5.5 零成本需求验证计划

在写任何销售材料之前，先做 10 次访谈。访谈对象来自已有网络：做多代理平台的工程负责人、受监管行业的 AI 交付负责人、 Agent 框架/MCP 网关的产品负责人。全部远程、零差旅、零礼品；不要求对方付费，也不要求对方部署。

#问题想验证什么
1最近一次“上游数字没依据、下游当证据”的事故是什么？痛点是否真实、是否高频
2现在怎么证明一句话是谁算的？拿得出记录吗？现有替代方案与缺口

6什么情况下你会拒绝它？反对意见与边界

访谈的成功判据不是“对方说好”，而是三件可观察的事： （1）至少 3 个买方描述了最近 6 个月内的真实触发； （2）至少 1 个买方愿意指定 POC 负责人； （3）至少 1 个买方能说出预算科目和审批人。 三条都没有，说明市场对象或切口错了，应该先改定位，而不是改产品。

5.6 细分结论

先打“多代理平台团队 + 合规暴露”这个交集，而不是整个可观测性市场。 这个交集的人数不多，但正好是“有预算、有触发、能自己做 POC”的买方； 他们成功后，会成为受监管客户的参考案例；受监管客户成功后，会成为框架厂商 OEM 的背书。 顺序是：开源入口 → 设计伙伴 → 付费试点 → OEM，不能跳步。

本章客户画像、单价与预算量级为作者假设（C），需用 10 次访谈证伪；外部采用数据为 D 级。不要在访谈中承诺合规认证或能力增益。
