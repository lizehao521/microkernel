## Persona

**陈岚**，34 岁，8 人研发团队负责人；团队用编码 Agent 交付业务代码，她负责收/退。

- **情境**：Agent 交来一版改动并声称「测试过了、问题修好了」，她要在收/退前确认声明是否成立。
- **目标**：不执行对方代码、不联网，10 分钟内逐条核对声明与盘上证据，留下可转发回执。
- **当前 workaround**：翻 Agent 总结、问开发者、手动看 diff 与测试日志，偶尔自己重跑测试。
- **挫败感**：声明真假难辨；证据散在文件/日志/轨迹/账本；聊天记录不是凭证；云端工具要上传代码；「核不了」常被当成通过。
- **「完成」长什么样**：每条关键声明能下钻到文件/行/日志/事件；第一屏分清 MATCH / MISMATCH / 核不了；一键导出回执。

**次 persona：周野**，27 岁，独立开发者；提交/发布前用同一套件自查，不想引入团队流程。

## 商业角度

- **为什么是现在**：编码 Agent 进入日常交付，「完成」这句话变便宜了，验收成为瓶颈；团队对代码上云、执行不可信代码有硬顾虑。
- **谁付费**：先用 Agent 写代码的团队负责人/工程组织；短期作者自己作为内部工具。
- **商业化**：pre-product，一次性许可或内部成本中心，不先做订阅。
- **战略意图**：cost-center（信任基础设施）。

## 桌上的方向

**方向 A**：单件回执台 —— 打开一份交付 → 跑核 → 读回执。
- 用户价值：把 CLI 与 HTML 回执包成可双击的本地窗口。
- 商业价值：最低成本把现有能力产品化。
- 最高风险假设：单件核对的频率足以让人愿意装一个桌面应用。
- 解决：机会 #1 #2

**方向 B**：团队收货台 —— 交付队列 + 三态分诊 + 收/退 + 回执历史 + 分享。
- 用户价值：只处理需要人判断的那几单；每单都有可追溯回执；退单理由能复用。
- 商业价值：桌面形态的真正理由：队列与审批，而不是把网页装进窗口。
- 最高风险假设：团队负责人愿意把验收搬进一个新工具，而不是继续在聊天里拍板。
- 解决：机会 #1 #2 #4 #5

**方向 C**：证据深潜器 —— 以轨迹/事件/账本为中心的时间线与下钻浏览器。
- 用户价值：审计与争议时能一路看到文件行、日志行、事件 seq。
- 商业价值：专业审计场景的差异化。
- 最高风险假设：存在高频的深潜需求，而不只是偶尔的争议复盘。
- 解决：机会 #2 #5

## 我押

**方向 B** —— 桌面端相对 CLI 的真正增量是「队列 + 分诊 + 收/退 + 历史」，这正好对应团队负责人每周重复的动作；A 作为首次打开的单件模式，C 作为回执里的下钻层。只做 A 的话，桌面形态没有必要；只做 C 的话，用户面太窄。B 把三者收进一个工作台。

## 关键假设

1. **（最关键）** 团队负责人愿意且需要每版交付后花 3–10 分钟逐条核对，而不是继续信任摘要；动作频率 ≥ 每周 3 次。
2. 可核声明能由 Agent 侧自动生成；否则核对成本只是从「看日志」转移到「写 JSON」。
3. 本地只读 + 不联网是采购/使用的硬条件，用户愿意为此放弃云端协作便利。

**信心水平**：合理推测但未验证（只有作者一次 dogfooding：真端点单 9 条声明 8 条自报、源码未交，回执判 UNVERIFIED）。建议先跑 3–5 人快速验证，不阻断本方向输出。

## 压测结果

**判断**：⚠️ 有条件成立

**理由**：机会点与现有能力高度对齐，且真端点单已经证明「把核不了如实印出来」有分辨力；但外部使用证据为零，队列频率与「谁生成声明」两个条件未验证。

**条件**：
- 找 3–5 位目标用户用真实交付跑一遍，观察是否打开声明行并做出收/退动作。
- 可核声明必须由 Agent 侧自动生成。
- 队列频率 < 每周 3 次时，把方向 B 降级为方向 A，不硬做团队流程。

**两个视角的综合**：
- **共同标记**：声明生成成本（工程视角：JSON 模板与工具链；业务视角：不能把核对成本转嫁给负责人）。
- **核心张力**：执行质量（逐条下钻、只读边界）vs 验证速度（10 分钟收/退、队列吞吐）。
- **必答的一个问题**：第一版是否只服务「一个人 + 一队列」，还是从第一天就做多人协作与权限？这决定信息架构，不是修复项。

## HMW 卡片（8 张，可直接进 workshop）

1. 我们如何能让陈岚在 10 分钟内看完一版交付的所有关键声明，从而做出收/退决定？—— 破冰卡：先让每个人说出今天验收一版 Agent 交付要花多久。
2. 我们如何能让「核不了」和「假完成」在第一屏就分开，而不是埋进表格？—— 做两组对照草图：按状态分组 vs 按声明顺序。
3. 我们如何能让 Agent 自动产出可核声明，从而不把写 JSON 的负担丢给负责人？—— 工程师与 Agent 使用者同组，现场写一条真实声明。
4. 我们如何能让一次验收留下可转发的回执，而不是聊天记录截图？—— 反向演示：只用回执向第三人解释为什么退单。
5. 我们如何能把多次交付排成队列，让负责人只处理需要人判断的那几单？—— 先排真实一周的优先级，再对照队列视图。
6. 我们如何能让证据下钻到文件行号/日志行/事件 seq，同时保持只读？—— 约束卡：任何下钻方案先回答「会不会执行被交付的代码」。
7. 我们如何能让独立开发者在提交前 3 分钟自查，而不需要团队流程？—— 独立开发者单开一组，避免团队流程思路压过个人场景。
8. 我们如何能让「退单理由」变成下一版可复用的核对项，从而越用越快？—— 后半场：把一条真实退单理由改写成下一条声明模板。
