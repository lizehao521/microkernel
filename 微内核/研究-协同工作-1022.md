# 研究 · 协同工作：程序运行时如何汇报，端侧如何跟上用户

- 日期：2026-10-22
- 方法：本机四套实物的代码与既有读数逐条核对（本次只做静态核对与既有捕获件复读，**没有新起服务、没有新跑测试、没有真人**）+ 五份外部标准
- 一句话边界：本文说的是「程序怎样让用户随时知道状态」，不证明任何一版实现已经做到；每处缺口都点名到文件行

---

## 0. 摘要（五条）

1. **协同不是「多打日志」，是「把一次运行拆成用户能核对的状态转移」**。每个转移要有身份（session/turn/seq）、进度（第几步/共几步）、证据（谁做的/数从哪来）、出口（停/补参/批准）。
2. **「看起来在流」不等于「真的在进行」**。AgentHub 的 `answer_delta` 是整段结论算完之后切块推的（`httpapi.go:92-98` 自己写明了）；真进度在 `tool_status/tool_result`，不在打字机效果。
3. **停下来的那一刻才是协同的考试**。停=结算：已完成的要留下，没走到的要显式记「没跑」+理由。pgagent 做了（`loop.go:278-350`），AgentHub 的循环里没有任何 `ctx.Done()` 判定（`agent.go:77-221`，静态核对），断线语义没有声明。
4. **端侧「及时」靠事件+游标，不靠轮询刷新**。SSE 标准本来给了 `id` + `Last-Event-ID` 的续传机制；本机两个 Web 实现都只发 `event/data`，没有 `id/retry`，所以现在的「重连」其实是新开一发，不是续上（`httpapi.go:128-135`、`main.go:216-227`）。
5. **对外可承诺的最小协同契约是七条**：先回执再干活、一转移一事件、每个数带出处、停=结算、危险动作先问后做、断线可续或明说不可续、界面只投影不自算。每条都能配一条会红的验收针（见 §8）。

## 1. 定义：什么叫「程序会协同」

用户在程序运行中只需要回答三个问题：

| 问题 | 需要的能力 | 没有它时的典型观感 |
|---|---|---|
| 现在在做什么？ | 受理回执 + 进展事件 + 「现在」行 | 按钮变成「处理中…」，之后一片安静 |
| 已经发生了什么？ | 结算账：完成/失败/被挡/没量到，各带理由 | 只在最后给一句结论，失败也说不清停在哪 |
| 我停了/断了以后会怎样？ | 中断语义 + 可续游标（或明说不可续） | 不敢点停，怕白跑；断了只能重来 |

再加一条底层条件：**这三个答案在程序那边必须是同一份账**。界面自己算一套数、后台账本另记一套，用户看到的和实际发生的就会在某个时刻对不上——那时候「协同」已经失败了，只是还没被发现。

本文把这件事拆成：

```
协同 = 三个同步 + 一份账
  同频   ：状态一变就有一个事件（在做什么）
  同步意图：用户随时能停/补参/批准（我要什么）
  同步后果：停下、断线、失败都结算（发生过什么）
  一份账 ：事件流是唯一源，界面只是投影
```

## 2. 外部标准给出的硬约束

| 标准 | 它规定了什么 | 对本项目的直接含义 |
|---|---|---|
| **WHATWG SSE**（Server-Sent Events） | 事件流字段 `event / data / id / retry`；客户端重连时发 `Last-Event-ID`，服务端据此续发后续事件 | 想要「断线续上」，必须有稳定的 `id` 和服务端重放；只发 `event/data` 的流，重连只能算新请求 |
| **MCP Progress** | `progressToken` 每个请求唯一；`progress` 必须递增；完成通知必须停止；双方应做限流；`total/message` 可选 | 进度必须有单调计数；「完成之后还在报进度」是协议违规；高频进度要节流 |
| **MCP Cancellation** | 用 `requestId` 指名取消；接收方**应**停止处理并释放资源；由于竞态，取消**不保证**一定生效 | 停是尽力而为：界面必须允许「已经完成、取消来晚了」这一态，不能假设停了就一定没发生 |
| **LSP Work Done Progress** | `$/progress` + token；`begin / report / end` 三段；`percentage / message / cancellable` | 进度要有明确的开头和**必须出现的 end**；可取消是进度对象的一等属性，不是另加按钮 |
| **Nielsen 响应时间三档** | 0.1s 感觉即时；1s 保持思路不断；10s 是注意力上限；超过 10s 需要百分比/确定性进度来安抚 | 回执 <0.1s；首个真实进展 <1s；10s 还没完就必须给「已完成/总数」或明确 ETA，不能只转圈 |

这五条合起来，给了一个很硬的判断：**没有 `id` 的流不是可续的流；没有 `end` 的进度不是进度；没有单调计数的进度无法证明在前进。**

## 3. 本机四套实物：成熟度对照

四套东西不是四个竞品，而是同一件事的四个切面。

| 能力 | 三件套内核 `chat/serve`（Node） | AgentHub `hubd`（Go） | pgagent（Go） | agentd（Go 宿主） |
|---|---|---|---|---|
| 受理回执 | 只有按钮文案「跑内核 + 模型推理中…」（`ui.html:40-45`） | `meta`：turn、规划器、工具数、步数上限、记忆条数（`agent.go:88`） | `meta`：session+turn，先于任何工作发出（`main.go:223-227`） | stderr 横幅：驱动、session、是否自主（`main.go:44-48`） |
| 步级进展 | **无**：整轮结束才一次性返回/打印（`runtime.js:104-185`、`repl.js:30-35`、`server.js:53-59`） | 7 类事件：meta/plan/tool_status/tool_result/answer_delta/result/done（代码去重现数） | `step` 事件逐步推 9 步，最后 `result`（`main.go:216-244`） | 逐发 `say` 日志；轨迹 HTML 在收口时才写（`loop.go:591-627`） |
| 解释/出处 | 每步 thought+observation；最终结论核数字出处 | 五档出处（measured/estimated/model_says/relayed/absent）+ `why` + `args_from` | 五档 + `Basis` + `traceSane` 11 条整列自洽（`loop.go:270-274`） | 每一步「依据是哪一格」+ 漂移检测 + 49 格轨迹（`trace.go:30-31`） |
| 用户介入 | 无（只能等） | Esc/停 → AbortController（`app.js:401-420`）；后端 TryLock 拒绝并发（`httpapi.go:71-75`）；缺参时 `ask` 停等 | `/api/stop` 点名停（`main.go:166-168`）；客户端断开也算停；每步之间检查 abort（`loop.go:77-94`） | SIGINT → 先交已落账再走（`main.go:82-90`） |
| 停下结算 | 未声明 | **未见显式「被打断」**：`RunTurn` 不查 `ctx.Done()`；断线只表现为工具调用取消，循环继续到上限 | **有**：收口照做、已落账保留、没走到的步逐条 absent+理由（`loop.go:278-350`） | **有**：六态退出码，打断=6（`main.go:15-21`） |
| 断线重连 | 无（POST 一次性） | 无 `id/Last-Event-ID`（`httpapi.go:128-135`） | 无 `id/Last-Event-ID`（`main.go:216-227`） | 进程级 checkpoint+resume（`main.go:38`、`loop.go:394-400`） |
| 并发/混列 | 单请求 | 第二发直接拒：「不排队、不混列」（`httpapi.go:71-75`） | W24 修前实测混列：一列 19 步（单发 13 步）；修后 13 格递增（`报告-收口.txt` W24 行） | 单进程 |

### 三条已量的读数

- **AgentHub 一发两目标**：25 帧，逐类为 meta 1 / plan 4 / tool_status 6 / tool_result 2 / answer_delta 10 / result 1 / done 1（`读数/SSE-列目录再统计.json` 自印）。
- **AgentHub 假端点一发**：12 步、56 帧（逐类数：meta 1 / plan 6 / tool_status 18 / tool_result 6 / answer_delta 23 / result 1 / done 1），出处 `读数/SSE-假端点-UTF8一发.json`。
- **agentd 一发**：49 格轨迹（输出侧 29 + 输入侧 20，`trace.go:30-31`），整份 HTML 在 `closeOut` 才落盘（`loop.go:623`）。

### 这张表说明什么

四套实现刚好凑齐了协同的四块，但没有一套四块都齐：

- 内核有**账与出处**，没有实时面；
- AgentHub 有**实时面与并发纪律**，断线结算没有声明；
- pgagent 有**停下结算**，没有可续游标；
- agentd 有**可续与六态退出码**，但汇报是「逐发日志 + 事后解剖」，不是实时协同。

所以缺的不是再写一个 Agent，而是把这四块合成一份**事件契约**。

## 4. 模型：三个同步 + 一份账

### 4.1 同频：进度不是日志，是状态转移

一个运行中的程序，对用户只需要维护三行：

```
现在：第 3/9 步 · analyze（为什么：问题里有「这段有什么问题」）
已经：完成 2、失败 1、被挡 0、没量到 0（每条没量到都带理由）
接下来：还有 6 步；步数上限 8；可停；补参可继续
```

日志是历史，**「现在」行才是协同**。日志可以滚，但「现在」行必须稳定可见。

事件必须对应状态转移，不是对应代码执行到哪一行：

```
turn_accepted → plan_selected → step_started → step_finished
                                   ↘ waiting_user
                                   ↘ warning（重试/退避/降级）
                … → turn_settled（跑完/被打断/失败/额度到）
```

没有状态变化的「假事件」（心跳、装饰性进度条）可以出现，但必须与进度分开计数：**心跳只证明活着，不证明在前进**。

### 4.2 同步意图：用户的手要能伸进去

三种介入，语义完全不同，不能混成一个「取消」：

| 介入 | 触发点 | 正确语义 | 错误做法 |
|---|---|---|---|
| 停 | 任意步之间 | 立刻停止推进；已发生的留下；未走到的记 absent | 断开连接就静默丢弃；或停了还继续把下一步跑完 |
| 补参 | 缺关键参数时 | 显式进入 `waiting_user`，说清缺什么、可给什么 | 猜一个参数继续跑（AgentHub 的 localPlanner 在扒不到参数时选择 `ask`，这是对的） |
| 批准 | 不可逆动作前 | 先问，再执行；拒绝就是拒绝 | 被门禁挡下后「顺手降级到另一个工具」——那是绕过同意（`agent.go:139` 注释写明） |

关键在**检查点位置**：必须在动作**之前**检查中止，而不是之后。pgagent 的 `beat()` 先看一眼再等（`loop.go:77-82`），注释写得很直白：不留窗口的「可中断」是散文。

### 4.3 同步后果：停=结算

一个能被信任的停止，至少交三样东西：

1. **停在哪**：第几步之后、当前在做什么；
2. **已经发生了什么**：成功/失败/被挡/没量到各几条，每条没量到的理由；
3. **没发生什么**：没走到的步骤逐条列出，并注明「根本没执行，不是执行了没结果」。

pgagent 的 `finish()` 就是按这个形状写的（`loop.go:298-321`）；它的测试 11 专门防「早停时把没跑的步补进轨迹」（`pgagent_test.go:312-327`），测试 12 防「已经落账、读回完成，却因为打断把 KPI 抹掉」（`pgagent_test.go:338-362`）。这两条正是协同里最容易骗自己的两个方向。

### 4.4 一份账：界面只是投影

AgentHub 的前端开头就写死了这条：

> 「数字与判据都由后端交，这里不自己算口径。」（`app.js:1-6`）

这是对的，而且它顺手做了一个很好的决定：**后端量出来的 0 要显示，不能像参考产品那样把 `retries=0` 藏掉**——藏掉等于删证据，只降视觉权重。

反过来，一旦界面自己算总数、自己推断「应该是 0」，它就会在某次失败时和账本对不上。对不上之后，用户看到的每一格都不可信了。

## 5. 事件契约（可直接实现）

### 5.1 一条事件的最小形状

```json
{
  "v": 1,
  "session": "s-7f3a",
  "turn": 12,
  "seq": 7,
  "ts": "2026-10-22T05:10:11.412+08:00",
  "kind": "step_finished",
  "step": { "no": 3, "name": "analyze", "tool": "text.stats" },
  "state": "failed",
  "evidence": "absent",
  "why": "文件读不到：路径不在 -fs-roots 里",
  "progress": { "done": 2, "total": 9 },
  "elapsed_ms": 812
}
```

强制字段只有五组：

| 组 | 字段 | 作用 |
|---|---|---|
| 身份 | `session / turn / seq` | 断线重连、去重、排序 |
| 转移 | `kind` + `step` | 这是什么状态变化 |
| 证据 | `state / evidence / why` | 成功还是失败、数从哪来、缺席为什么 |
| 进度 | `progress.done / total`（可缺） | 证明在前进；缺了就不能声称有进度 |
| 时间 | `ts / elapsed_ms` | 三档时延预算的分子 |

### 5.2 七条契约

1. **先回执再干活**：收到请求先发 `turn_accepted`（session、turn、计划、上限、是否可续、怎么停），再开始第一次选件。目标 <0.1s。
2. **一转移一事件，seq 严格递增**：同一 `(session,turn)` 内不重复、不回退；重放两次得到同一序列。
3. **每个数带出处，缺席带理由**：五档（量到/本机推/端点说/外部转述/没量到）至少要有「量到」与「没量到」的区分；`absent` 没有 `why` 就是缺陷。
4. **停=结算**：任何终止都要有 `turn_settled`，带 `stop / stop_why / 已完成计数 / 未走到的步骤`；`stop` 至少覆盖：跑完、要补参、步数上限、被打断、门口挡、内部错。
5. **危险动作先问后做，拒绝不找替身**：`fs_write/exec/net` 这类动作，批准事件必须出现在 `step_started` 之前；被拒后不得降级到同类工具。
6. **断线要么可续，要么明说不可续**：SSE 发 `id: <session>:<turn>:<seq>`，支持 `Last-Event-ID` 重放；做不到就在 `turn_accepted` 里写 `resumable:false`，界面明示「断开即取消」。
7. **界面只投影账，不自算**：所有计数、百分比、加总都由后端交；前端只做格式化与三态显示；屏幕上出现后端没交的字段（`undefined/NaN/[object Object]`）就是缺陷。

第 7 条可以再加一条工程约束：**有界**。事件日志、历史列表、会增长的容器都要有上限；背压时最先保的不是滚动日志，而是 `turn_settled` 这个终止事件。

### 5.3 三档时延预算

| 截止 | 必须发生什么 | 依据 | 本机现状 |
|---|---|---|---|
| 0.1s | 受理回执（含 turn 身份与停止入口） | Nielsen 0.1s 即时感 | pgagent 先发 meta，达标；AgentHub meta 在 RunTurn 开头，基本达标；内核只有按钮文案，不达标 |
| 1s | 首个真实进展（第 1 步开始/计划已选） | Nielsen 1s 思路不断 | AgentHub/pgagent 达标；内核要等整轮结束，不达标 |
| 10s | 确定性进度（done/total）或明确 ETA；否则必须解释为什么还没有 | Nielsen 10s 注意力上限 | 本机没有一版在 10s 时主动解释；长任务读数 NOT_RUN（见 §9） |

超过 10s 还在转圈，等于把「在算」还是「卡死」的判断成本推给用户。正确做法不是加动画，而是给一个可核对的计数。

## 6. 端侧如何「及时跟进」

这里的「端侧」按用户侧运行时+界面理解（本机进程、浏览器页面、桌面壳都算）。及时跟进不是刷新得快，而是三件事：

### 6.1 事件驱动，不轮询

SSE/流式是主通道；轮询只能做兜底。事件到达就投影，状态没变就不发。否则「实时」会退化成高频噪音。

### 6.2 游标：断线后从哪继续

SSE 的 `id` + `Last-Event-ID` 是标准给的现成机制。实现要点：

1. 每条事件写 `id: <session>:<turn>:<seq>`；
2. 服务端把事件落进 append-only 日志（与账本同一套纪律）；
3. 重连时读 `Last-Event-ID`，从该序号之后重放；
4. 重放不出重复（幂等），也允许客户端按 `seq` 去重；
5. 如果服务端没有日志，就在受理事件里写 `resumable:false`——**诚实地说不可续，比假装能续更协同**。

本机两个 Web 实现都没有第 1 步，所以现在的「断线」只能靠客户端主动中止或用户重发。这不是「可续」，是「重来」。

### 6.3 可打断窗口：在动作之间，不在动作之后

- 长动作开始前检查一次 abort；
- 等待/退避期间可被 abort 唤醒（pgagent 的 `beat()` 就是这个形状）；
- 不可逆动作写成两步：`approval_requested → approval_granted → step_started`；
- 停下后不再启动任何新动作，但允许当前动作自然收尾并结算。

pgagent 的 `-step-delay` 不是装饰：没有延时，一圈几十毫秒就跑完，人根本来不及点停。它把「可中断」变成一个可实测的窗口（`loop.go:52-53`、`main.go:115`）。AgentHub 的 `StepDelay` 同理（`httpapi.go:87-98`），但必须标明这是演示节奏，不是真实工作量。

### 6.4 背压与有界

- 一发一把锁：并发请求要么排队并标明位置，要么直接拒绝（AgentHub 选择拒绝，并写明「不排队、不混列」）；
- 事件日志按 `(session,turn)` 分段，超限时先落终止事件；
- 界面里会增长的容器必须有界；用户往上翻旧记录时不要强行拽回底部（pgagent W22 的读数：上翻后 scrollTop 保持 0，发完新发仍是 0）；
- 只画一发：W24 实测过，连点两次会让两发的步骤写进同一列——修前那一列 19 步，而单发只有 13 步；修后 13 格递增。

## 7. 十个反模式（每条都有本机证据）

| # | 反模式 | 为什么坏 | 本机证据 |
|---|---|---|---|
| 1 | **黑箱等待**：按钮变成「处理中…」，之后没有「现在」行 | 超过 10s 用户分不清慢和死 | 内核面板 `ui.html:40-45`；整轮结束才 render（`server.js:53-59`） |
| 2 | **批量日志冒充进度**：步骤是真的，但整轮结束才一起打印 | 回答的是「发生了什么」，不是「正在做什么」 | `repl.js:30-35`：`await runTurn` 之后 `forEach(showStep)` |
| 3 | **假流式**：整段答案算完再切块推，界面像在打字 | 用户以为模型在逐步思考；实际进度与动画无关 | AgentHub `httpapi.go:92-98` 注释自认「流式的是已经算完的结论」 |
| 4 | **装饰性进度**：用人为延时把步骤拉长，看起来在动 | 把演示节奏当成工作量，会掩盖真实的慢步骤 | `StepDelay`（`httpapi.go:87-90`）、pgagent `-step-delay`；后者至少标明是为可打断窗口 |
| 5 | **断开不结算**：连接断了，循环没有「被打断」这一态 | 账上可能多跑几步，用户却以为已经停了 | AgentHub `RunTurn` 无 `ctx.Done()` 判定（静态核对 `agent.go:77-221`）；此形未实跑，记未量到 |
| 6 | **无 id 的 SSE 冒充可续**：重连只能新开一发 | 用户会以为接着跑，实际重来；重复副作用 | `httpapi.go:128-135`、`main.go:216-227` 都只写 `event/data` |
| 7 | **并发混列**：两发的步骤进同一列 | 界面把两次运行混成一次，读数全错 | pgagent W24：修前 19 步 vs 单发 13 步；修后 13 格递增（`报告-收口.txt`） |
| 8 | **事后轨迹冒充实时**：跑完才写的解剖页被说成「过程可见」 | 审计价值真实，但不能在运行中回答「现在怎样」 | agentd `closeOut` 才 `writeTrace`（`loop.go:591-627`） |
| 9 | **把没量到写成 0**：缺席不写理由，或折叠成零值 | 用户会把「没测」当成「测了是 0」 | AgentHub/pgagent 的五档与 absent+why 就是为此；pgagent `traceSane` 有「缺席没理由」「没量写成measured」两条（`loop.go:270-274`） |
| 10 | **打断时补步**：把没跑的步骤也写进轨迹，看起来跑完了 | 停下来反而制造假账 | pgagent 测试 11 专门钉这一形（`pgagent_test.go:312-327`） |

## 8. 对 `cmd/agentd` / 三件套内核的落地清单

宿主 `cmd/agentd` 已经有三件最难的东西：**六态结束原因**（`main.go:15-21`）、**SIGINT 先交账再走**（`main.go:82-90`）、**checkpoint+resume**（`main.go:38`、`loop.go:394-400`）。缺的是把它们投影成用户能实时看见的事件面。

### 8.1 最小改动（不碰内核 v1）

| 优先级 | 动作 | 落点 | 说明 |
|---|---|---|---|
| P0 | 在宿主循环现有的 `r.say` 位置加 `emit(event)` | `cmd/agentd/loop.go` | 只加事件，不改内核调用与数值逻辑 |
| P0 | 事件按 `(session,turn,seq)` 写 append-only JSONL | 与 checkpoint 同目录 | 账本纪律：先落盘，再上屏 |
| P0 | `turn_accepted` 先于第一次 `kernel.check_call` | 宿主入口 | 带 session/turn/计划/上限/停止入口/是否可续 |
| P0 | 停止接口 + 结算事件 | 宿主 HTTP/信号层 | 复用六态：被打断=6；`turn_settled` 带未走到的步 |
| P1 | SSE 输出，`id: session:turn:seq`；支持 `Last-Event-ID` 重放 | 宿主 HTTP 层 | 做不到就写 `resumable:false`，界面明示 |
| P1 | 10s 兜底提示：done/total 或「为什么还没到」 | 宿主循环 | 超时不是报错，是汇报 |
| P1 | 三行界面：现在 / 已经 / 接下来 | 复用 AgentHub 三栏布局 | 只投影，不自算；保留「量到的 0」 |
| P2 | 事件流与 49 格轨迹同源 | `trace.go` | 一份账两个投影，避免两处各算版本 |

### 8.2 八条验收针（每条都要能红）

1. **回执针**：`turn_accepted` 距请求入口 >100ms ⇒ 红。
2. **序号针**：同一发内 `seq` 不严格递增或有重复 ⇒ 红。
3. **缺席针**：任一 `absent` 事件没有 `why` ⇒ 红。
4. **结算针**：打断后 1s 内没有 `turn_settled`，或已完成计数与打断前不一致 ⇒ 红。
5. **补步针**：打断后轨迹里出现未执行的步骤 ⇒ 红（对照 pgagent 测试 11）。
6. **续传针**：重连后事件序列不能从 `Last-Event-ID` 之后接上，且受理事件又没写 `resumable:false` ⇒ 红。
7. **混列针**：两个并发请求的步骤进入同一 `(session,turn)` 列 ⇒ 红。
8. **投影针**：界面出现后端未交的字段（脏字栏 >0）或前端自算的加总与后端不一致 ⇒ 红。

前六条可以在 `scripted` 驱动上跑；第七、八条需要真起服务与页面。真模型端点仍按现纪律记 **NOT_RUN**，不写成 0。

### 8.3 与内核 v1 的边界

内核 v1 已冻结；事件层属于宿主，不属于内核。宿主只消费内核已有的 `check_call / record_call / read_back / verify / tally`，事件里的「依据」直接引用回读到的格名与值。这样既不动冻结面，又能让「循环住在内核之外」这件事在用户侧可见。
